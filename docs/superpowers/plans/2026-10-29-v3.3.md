## Task 1 · The taskbar shows the old icon

### Cause (verified)

- `assets/icon.ico` is the current cat head: 9 frames (16, 20, 24, 32, 40,
  48, 64 as 32-bit DIBs; 128, 256 as PNG), rendered and checked. The installed
  `%LOCALAPPDATA%\Programs\Vale\vale.exe` embeds exactly these frames (byte
  match), none of the older icons (`2727ae6`, `64eefba`). Nothing in `src/`
  draws an older logo (`fn logo` in `settings_controls.rs` is the cat).
- The only Vale window with a taskbar button is Settings
  (`src/ui/settings.rs:660`, no `WS_EX_TOOLWINDOW`, no parent). It sets its
  icons from resource 1 with `WM_SETICON` (`settings.rs:503-541`), so
  Alt+Tab gets the cat. The island (`src/ui/window.rs:41-63`) and editors are
  tool windows (no button); their classes have no icon (island) or the shared
  resource (editors, `editor.rs:823`).
- **The Windows 11 taskbar does not use `WM_SETICON` for the button.** A probe
  (a WinForms window in `powershell.exe` with `Form.Icon` = `assets/icon.ico`,
  then a capture of the taskbar) showed the PowerShell exe icon, not the cat;
  with `ShowInTaskbar = false` the button went away, so it was that window.
  The button shows the app's icon resolved from the **exe path** (and the
  Start Menu shortcut that targets it) through Explorer's icon cache.
- The path never changed (`vale.exe` since v3.1), so Explorer keeps the v3.1
  "eared tile" it cached for `vale.exe,0` / `Vale.lnk`. `install.ps1:100`
  overwrites the exe in place and `install.ps1:107-114` rewrites the shortcut
  without telling the shell (no `SHChangeNotify`, no `ie4uinit`). Not pinned
  on this PC (`User Pinned\TaskBar` has no Vale), no sparse package
  registered, so neither is the cause here.
- Not verifiable from outside: Explorer's in-memory image list. A fresh
  `SHGetFileInfo` in another process already returns the cat, which fits
  "the on-disk cache was refreshed, the running Explorer was not".

### Design

1. **Installer** (main fix): after copying the exe and saving the shortcut,
   tell the shell: `SHChangeNotify(SHCNE_UPDATEITEM, SHCNF_PATHW|SHCNF_FLUSH)`
   for the exe, `Vale.lnk` and a pinned
   `%APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar\Vale.lnk`
   if present, then `SHChangeNotify(SHCNE_ASSOCCHANGED, SHCNF_IDLIST)`, then
   `& "$env:WINDIR\System32\ie4uinit.exe" -show` if it exists. All
   best-effort (`try {} catch {}`), never fatal. Set
   `$link.IconLocation = "$Exe,0"` explicitly. Do this *before* step 7 starts
   Vale. Same for a zip install (same script).
2. **App, once per new version** (covers a manual copy over the old exe):
   at start, if the stamp file `<data dir>\shell-icon.txt` does not hold
   `CARGO_PKG_VERSION`, call `SHChangeNotify(SHCNE_UPDATEITEM, SHCNF_PATHW)`
   for `current_exe()` and `SHCNE_ASSOCCHANGED`, then write the stamp. No
   `SHCNF_FLUSH` here (async, never blocks the UI thread). Decision is pure
   and tested with a temp stamp path.
3. **Island class icon**: give `ValeWindow` (`window.rs:41`) the shared class
   icons from `app_icon::class_icons` like the editor, so Task Manager and any
   shell surface that asks the window gets the cat. Cheap, no behaviour change.

What the installer cannot do: purge Explorer's in-memory cache without
restarting Explorer (do **not** kill `explorer.exe` or delete
`iconcache_*.db`; too disruptive for an installer). If a pinned icon or the
running taskbar still shows the old mark, the owner signs out/in or restarts
Explorer once; that is said in the installer's last lines only when a pinned
Vale shortcut exists. Rejected: an explicit AppUserModelID (changes grouping
and pins, does not bust the cache by itself).

## Task 2 · Stay-behind: a smooth rise

### Current behaviour

`App::follow_behind` (`src/app.rs:3116`) asks `Behind::decide`
(`src/behind.rs`) and calls `set_front` (`app.rs:3158` →
`IslandWindow::set_front`, `window.rs:119`), a single
`SetWindowPos(HWND_TOPMOST)`: the island, covered by a window, pops in at
full opacity in one frame. Lowering is one `SetWindowPos(HWND_BOTTOM)` (the
window in front simply covers it again, which reads naturally).

### Design

- A **rise** when the island goes Bottom → Top **and was covered**: drawn
  from opacity 0 and 8 dip higher (sliding down out of the screen's top
  edge) to 1 and 0 over 180 ms, ease-out cubic. With Motion not Full
  (`self.motion().moves()` false: Saver, Off, or Energy Saver) only the fade,
  120 ms. Lowering stays instant (out of scope; see risks).
- "Covered" is read once, at the raise: `WindowFromPoint` at the centre of
  the drawn island (`renderer.island_px()` + `screen_origin`) and
  `GetAncestor(GA_ROOT) != self.hwnd`. An island that was already visible
  (nothing over it) rises without a fade, so it never blinks out.
- Pure state in `src/behind.rs`: `pub struct Rise { start, ms, drop_dip }`,
  `Rise::new(now, moves)`, `Rise::at(now) -> (f32 /*opacity factor*/, f32
  /*dy in dip, <= 0*/)`, `Rise::running(now)`, and `pub fn rise_wanted(was: Z,
  now: Z, covered: bool) -> bool`. Constants `RISE_MS = 180`,
  `RISE_SAVER_MS = 120`, `RISE_DROP_DIP = 8.0` with a "why" comment.
- `App`: `rise: Option<Rise>`. In `follow_behind`, before `set_front(true)`
  from Bottom, read covered; if `rise_wanted`, set `rise` and
  `ensure_clock()`. `animating_at` (`app.rs:2726`) also returns true while
  the rise runs, so frames run only for those 180 ms; `animate` clears it when
  done. `draw` (`app.rs:4014`, the `renderer.draw` call at `app.rs:4148`)
  applies it through a pure helper `rise_frame(shape, opacity, rise, now) ->
  (ShapeRect, f32)` (multiply opacity, add dy to `shape.y`). `sync_behind`'s
  "setting off / fullscreen" path and `reset` drop any rise (snap to 1).
- Power: no new timer, no poll change; the frame clock only during a rise
  ([[bata-idle-power-budget]]).

### Files

`src/behind.rs`, `src/app.rs` (`follow_behind`, `animating_at`, `animate`,
`draw`, a small `island_covered`), `docs/memory/stay-behind.md`.

### Tests first

In `src/behind.rs`:
- `a_covered_island_rises_only_from_the_bottom`: `rise_wanted(Bottom, Top,
  true)`; false for `(Bottom, Top, false)`, `(Top, Top, true)`, `(Top,
  Bottom, true)`, `(Bottom, Bottom, true)`.
- `a_rise_fades_in_and_slides_down_over_its_time`: `Rise::new(t0, true)`: at
  t0 `(0.0, -8.0)`; at 90 ms opacity strictly between 0 and 1 and dy between
  -8 and 0, opacity past 0.5 (ease-out); at 180 ms and after `(1.0, 0.0)`;
  `running` true before 180 ms, false from 180 ms.
- `a_rise_without_motion_only_fades_and_is_quicker`: `Rise::new(t0, false)`:
  dy always 0, done at 120 ms.
- `a_rise_never_goes_backwards`: opacity non-decreasing over 0..=200 ms in
  1 ms steps; dy non-decreasing towards 0.

In `src/app.rs` tests:
- `a_rising_island_is_drawn_dimmer_and_higher`: `rise_frame` with a rise at
  its start returns opacity × 0 and `y - 8`; with `None` or a finished rise,
  the input unchanged; a morph's own opacity (0.5) is multiplied, not
  replaced.

## Task 3 · A drop opens the shelf and keeps it

### Current behaviour

- Drag enter: `shelf_ole` posts `ShelfDragOver(true)` →
  `App::on_shelf_drag` → `Event::ShelfDrag(true)` (`src/state.rs:525`) sets
  `shelf_held`, the panel opens on the shelf.
- Drop: `App::on_shelf_drop` (`src/app_shelf.rs`, ~line 80) adds the paths,
  applies `ShelfDrag(true)` again and arms `TIMER_SHELF_HOLD` for
  `SHELF_HOLD_MS` = 2.5 s; then `on_shelf_hold_timer` applies
  `ShelfDrag(false)` → `shelf_held = false` (`state.rs:530`) → the panel
  closes unless hover holds it.
- During the OLE drag the island gets no mouse messages, so after the drop
  `hover` is false. The first move starts the dwell; `Hover(true)` clears
  `shelf_held` ("hover takes over", `state.rs:426`), and leaving closes it
  (Hover mode). So: a still pointer → closed after 2.5 s; a pointer moved
  away → closed at once. That is the collapse the owner sees.
- A leave before the dwell fired sends nothing: `HoverTracker::on_leave`
  (`app.rs:4200`) only returns `Hover(false)` when the visit expanded.

### Design

- New pure event `Event::ShelfDropped` (App applies it after adding the
  paths, instead of `ShelfDrag(true)` + the 2.5 s timer). Reducer (not in
  fullscreen): page Shelf, `collapsed = No`, `shelf_held = false` (the drag is
  over), **`latched = true`**, and in Hover mode a new field
  `shelf_drop: DropVisit { No, Here, Left }` = `Here`.
- Latched means the existing rules hold it: it survives the pointer leaving,
  `TIMER_OUTSIDE` runs (`outside_click_wanted`), a click outside
  (`Event::Dismiss`) closes it, a card click collapses it, fullscreen and a
  mode change clear it. HoverStay and Click modes need nothing more: "stays
  until a click outside" is their normal rule.
- Hover mode, "normal rules afterwards": the drop's own visit does not end
  it. `Hover(false)` or the new `Event::ShelfDropLeft` (App sends it from
  `on_mouse_leave` when `on_leave()` returns `None` and the reducer says
  `shelf_drop_here()`) turn `Here` into `Left`. The next `Hover(true)` with
  `Left` hands over: `latched = false`, `shelf_drop = No`; hover holds it and
  leaving closes it as usual. A page change (wheel) in Hover mode also hands
  over (`latched = false`, `No`). Invariant in the post-process: `!latched`
  ⇒ `shelf_drop = No`.
- `ShelfDrag(false)` (the 600 ms leave timer, an empty drop) only clears
  `shelf_held`, never the drop's latch. `on_shelf_drop` kills a pending
  `TIMER_SHELF_HOLD`; `SHELF_HOLD_MS` goes (`TIMER_SHELF_HOLD` stays for the
  600 ms leave).

## Task 4 · Search: apps, files and folders

### Current behaviour

`src/search.rs` (pure apart from `index_start_menu`): apps from Start Menu
`.lnk` (indexed once on a thread, `app_search.rs:152`), 16 settings pages, a
calculator, a web row; ranking prefix 3 > word 2 > substring 1; at most
`MAX_RESULTS` = 6 rows (calc first, web last). Rows draw a fixed glyph and a
kind word (`render_panel.rs:1891-1950`); the layout fits exactly 6 rows of 28
dip (`panel_layout.rs:2000`; 254 dip of content, 214 after the field; a strip
leaves 190). `search_again` (`app_search.rs:281`) resets the highlight to 0.
No file search (`search.md`: "later").

### Design

**Sources**
- Apps, settings, calculator, web: kept as they are.
- Files and folders: names under Desktop, Documents, Downloads, Pictures,
  Videos, Music (`SHGetKnownFolderPath` `FOLDERID_*`, redirected/OneDrive
  paths as Windows gives them). Our own walker, not Windows Search: indexing
  may be off or exclude folders, OLE DB from Rust is heavy, and a walker is
  testable on temp trees.

**Walk** (`src/search_files.rs`, new; pure over the roots it is given)
- `pub struct FileRoot { pub kind: RootKind, pub path: PathBuf }`;
  `default_roots()` (impure, never in tests); `dedupe_roots` drops a root
  inside another (Pictures inside a redirected Documents) and the walk never
  enters a path that is another root.
- Breadth-first per root, so shallow items (the likely ones) are kept before
  any cap bites. Limits, with reasons in comments:
  - `FILE_DEPTH = 5` folders below a root (Documents\A\B\C\D\file); deeper is
    mostly code trees and archives.
  - `FILE_ROOT_MAX = 10_000` entries per root, so a huge Documents cannot
    starve Desktop or Downloads; `FILE_TOTAL_MAX = 30_000` overall (~6 MB of
    paths in memory, a walk of a few hundred ms on an SSD).
- Skipped: hidden or system entries, names starting with `.`,
  `node_modules`, `__pycache__`, `$RECYCLE.BIN`, `.lnk` files (apps come from
  the Start Menu). Never follows a reparse point (symlink, junction); a
  folder with `FILE_ATTRIBUTE_RECALL_ON_OPEN` (cloud, listing would download)
  is listed but not entered. Files are never opened (no hydration).
- Each `FileEntry { name, lower, path, root: RootKind, parent: Option<String>
  /* folder under the root, for the subtitle */, is_dir, size, modified }`.
  Size and modified come free from the directory listing (`DirEntry`
  metadata), already off the UI thread.
- When: on every way in (`focus_search`, with `start_search_index`), on a
  short-lived thread `vale-search-files`, only if the last walk started more
  than `FILE_FRESH = 30 s` ago; the old index answers meanwhile. Sent back as
  `Event::SearchFiles(Vec<FileEntry>)`. In memory only, never written to
  disk; nothing runs while the search is closed.

**Matching and rows** (`search.rs`)
- `search(line, apps, files, lang, labels)`. Apps and settings match from the
  first character; files and folders from `FILE_MIN_CHARS = 2` (trimmed,
  counted in chars; a `?` line stays web only).
- Files rank by `match_score` on the name, then folders before files, then
  newer `modified` first, then shorter name.
- Rows stay at `MAX_RESULTS = 6` (the layout's limit). Order: calculation,
  apps/settings, files/folders, web. Room = 6 − calc − web. File rows: at
  most `FILE_ROWS_MAX = 3` and never so many that fewer than `APP_ROWS_MIN =
  2` app rows remain when apps match; apps take the rest; leftover room goes
  to whichever kind still has hits. Grouped (not interleaved) so the
  keyboard path to apps stays predictable.
- `Kind::File`, `Kind::Folder`; `Action::OpenPath(PathBuf)` run through the
  existing `shortcuts::Action::OpenPath` (as a shelf card), with
  `AllowSetForegroundWindow` like apps.
- `SearchResult` gains `path: Option<PathBuf>` (detail key) and the base
  subtitle: file "Unduhan · 2,4 MB" (root label, `› parent` when nested),
  folder "Dokumen › Proyek"; the count/app size are added when known.

**Details in the background** (`src/search_details.rs`, new)
- One parked worker thread `vale-search-details` (blocks on its channel, zero
  cost idle), started on the first open, COM STA inside. Requests carry a
  `generation`; the worker drains to the newest request and drops older ones.
  Answers `Event::SearchDetail { generation, key, detail }` + `WM_APP_EVENT`.
- Details: **icon** (`IShellItemImageFactory::GetImage` 32 px,
  `SIIGBF_ICONONLY`, never a content thumbnail; HBITMAP → `GetDIBits` →
  premultiplied BGRA), **folder count** (direct children that are not
  hidden, capped at 999 → "999+"; not for a recall-on-open folder), **app
  install size** (resolve the `.lnk` target with `IShellLinkW`, match an
  Uninstall entry (HKLM 64/32-bit, HKCU; read once per worker) whose
  `InstallLocation` contains the target or whose `DisplayIcon` exe is the
  target; `EstimatedSize` KB; shown only when found).
- `App` keeps `details: HashMap<PathBuf, Detail>` (cap 256, cleared when it
  grows past it) and asks only for shown rows missing from it
  (`wanted_details`, pure). An answer redraws the search; it never re-ranks.
  Results show at once, details fill in.
- Selection: a pure `keep_selection(old, at, new)` keeps the highlight on the
  same result (by action) when the app index, the file index or a re-search
  arrives; else 0.

**Drawing**
- `SearchView` gains `details` (icon pixels + extra note by path) and
  `indexing: bool`. A row draws the shell icon when present (cached D2D
  bitmap per path in `Renderer`, like `clip_thumbs`; cleared with the
  target), else a glyph: `Icon::Grid` app, `Icon::Folder` folder,
  `shelf::icon(shelf::kind_of(..))` for files. Subtitle at the right as now
  (≤ 40 % of the row).
- With ≥ 2 characters, no file rows yet and the first walk running: a quiet
  "Membaca berkas…" hint where the empty message would go only if there are
  no rows at all.
- Demo scene `search` and a new `search-files`: made-up apps and files
  (`demo.rs:2121`), never the real Known Folders; capture via
  `scripts/capture-screenshots.ps1 -Only search,search-files`.

### Risks

- Windows Search would find more (contents, other drives); this is names in
  six folders by design. Say so in the note.
- Running files from Downloads runs them, as a double-click would.
- `GetImage` for some file types loads a shell extension on the worker
  thread; it is off the UI thread, but a bad extension can hang the worker
  (the UI still shows glyphs). The worker drains stale requests, so it
  recovers once the call returns.
- The breadth-first walk with caps may miss a deep file in a huge tree; the
  caps are constants, easy to tune.
